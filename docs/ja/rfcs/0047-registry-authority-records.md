# RFC 0047: レジストリ権限レコードと最新状態での認可

[English version](../../rfcs/0047-registry-authority-records.md)

- Status: accepted
- Authors: project contributors
- Created: 2026-10-31
- Last updated: 2026-10-31
- Tracking issue: M5-E01, M5-D02
- Supersedes: none; elaborates RFC 0046
- Superseded by: none

## 概要

レジストリトランザクションが使用する、上限付き権限レコードと純粋な認証・認可検査を規定する。不透明トークンは、明示的に設定したレジストリと HTTPS origin の組の内部でのみ、有効な登録主体を識別する。付与された権限と現在の所有者情報から操作を許可する。以前の検査成功は、後のコミットを認可しない。

## 動機

RFC 0046 はトークンスコープ、失効、コミット時検査を定めているが、厳密な内部レコード形式は補足仕様に委ねている。先に公開処理を実装すると、呼び出し側が指定した主体や過去の認可結果を受け取る API に陥りやすい。D02 のトランザクションより先に E01 の純粋なポリシーを実装し、D02 のロック内で再読込したコミット済み状態に対して呼び出す。

## 目標

- ポリシー評価前に、有限で未知フィールドを認めない権限レコードを検証する。
- 資格情報を論理レジストリと正規 origin の両方に束縛する。
- 認証、操作権限、現在の所有権を区別する。
- 秘密を永続化、診断、通常のデバッグ表示から除外する。
- 期限、失効、所有者削除、時計の巻き戻りをテストで観測可能にする。

## 非目標

- HTTP サービス、TLS 終端、資格情報生成、ログイン、ID 連携。
- 権限の保存、資格情報登録・失効トランザクション、所有者変更、監査永続化。
- パッケージ署名、本番 consumer、新しいソース言語 capability。
- リクエスト全体の時間特性保証、メモリ解析への防御、信頼したホスト・運用者への防御。

## ガイドレベルの設計

公開用資格情報はパッケージ名ごとの明示的な権限を持つ。新規名には `claim` と `publish` の両方が必要で、別バージョンの公開には `publish` と現在の所有者資格が必要である。`parser` の `publish` 権限では `lexer` を公開できず、管理者トークンは通常の公開トークンの代わりにならない。プレビューが成功していても、所有者削除や資格情報失効の後は操作できない。

クライアントは明示的で上限付きの秘密入力からのみ bearer を受け取る。将来の HTTP アダプターはリダイレクトせず、設定済み origin に送信する。サーバーは主体 ID、時刻、所有者一覧、過去の認可レポートを呼び出し側が与える権限根拠として受け取らない。

## 参照セマンティクス

### 権限レコード profile 1

ホスト専用交換オブジェクトのフィールド順は `format: "lang-registry-authority"`、`schema: 1`、`registry`、`origin`、`time_floor`、`principals`、`tokens`、`packages` とする。RFC 0046 の正規 JSON（2 空白の pretty encoding と末尾 LF）、整数のみ、重複・未知フィールド禁止、別表記禁止に従う。最大 16 MiB、JSON の最大入れ子深さは 16 とする。無制限な型付き割当前にバイト数・深さ・要素数を制限する。これは信頼されたレジストリ状態の検証済みビューであり、署名文書でも、ネットワーク利用者が提出する権限根拠でもない。

`registry` とパッケージ名は RFC 0046 の名前文法に従う。`origin` は同 RFC の正規 HTTPS profile に従い、暗黙の正規化、既定ポート 443 の明記、先行ゼロ付きポート、URL の接尾部を拒否する。それ以外の 1–65535 の十進ポートは許可する。レジストリ ID だけでは audience 束縛として不十分であり、同じラベルでも origin が異なる設置先は別サービスである。署名ルートは別の領域であり、bearer の audience ではない。受理時は独立した信頼済みホスト設定から expected registry/origin を受け取り、外側 identity の不一致を拒否する。レコード自身が信頼するサービスを選べない。

| コレクション | レコードのフィールド順 | 順序と上限 |
| --- | --- | --- |
| `principals` | `id`, `active` | 32 文字の小文字 hex ID の厳密な昇順。最大 4,096。 |
| `tokens` | `id`, `principal`, `registry`, `origin`, `authenticator_sha256`, `issued`, `expires`, `revoked`, `grants` | 32 文字の小文字 hex ID の厳密な昇順。最大 4,096。 |
| Token `grants` | `action`, `name` | `(action の表記, name)` の厳密な昇順。1–128。action は `admin`、`claim`、`owners`、`publish`、`yank`。名前は完全一致で wildcard を認めない。 |
| `packages` | `name`, `owners` | パッケージ名の厳密な昇順。最大 1,024。存在は名前が取得済みであることを意味する。 |
| Package `owners` | 主体 ID 文字列 | 重複しない ID の厳密な昇順。1–128。 |

各トークンの主体と各所有者は登録済み主体を参照する。無効な主体は過去のメンバーとして残せるが、各パッケージは少なくとも 1 人の有効な所有者を保持する。トークン ID と authenticator hash は一意で、曖昧な一致レコードを受理しない。トークンの registry/origin は外側のサービスと一致させる。`authenticator_sha256` は厳密に 64 文字の小文字 hex で、RFC 0046 の指定どおり一様乱数の 32 バイト bearer から計算し、bearer 自体ではない。未登録の初期ビューでは主体・トークン・パッケージの各コレクションを空にできる。

時刻は `0..=253402300799` の整数とする。`issued < expires` および `expires - issued <= 604800` を要求し、時刻 floor も同じ範囲とする。失効済み・期限切れトークンもレコードとしては有効で、認証時に拒否する。レコード検証によって再有効化しない。

完全な不変レジストリ状態は、意味を変えずにこれらのフィールドまたはこの閉じた権限オブジェクトを埋め込む。D02 は永続化前に generation/HEAD/監査の完全な形式を規定し、取得済みパッケージ・所有者・リリースの整合性を検証する。E01 は独立して書き込める権限ファイル、第 2 のコミット点、新しい復旧経路を追加しない。RFC 0046 の順序要件を具体化し、権限フィールドは E01 より前、残りのトランザクション・監査フィールドは D02 より前に定める。

### 秘密入力と認証

秘密入力は厳密に 64 バイトの小文字 hex と、任意の 1 個の末尾 LF のみとする。CRLF、前後の空白、大文字、途中までの入力、余分なバイトを拒否する。上限付き reader は許可入力と超過を区別するため最大 66 バイトまで読み、無制限なストリームを読み切らない。HTTP ヘッダー解析は別アダプターとし、厳密な `Bearer ` 接頭辞 1 個と 64 バイトの小文字 hex を受け取り、末尾 LF と Authorization ヘッダーの重複を認めない。

デコードした bearer は非公開でシリアライズできない秘密 wrapper のみに保持する。`Debug` は秘匿表示し、暗黙の文字列・display 変換や自動 clone を持たせない。既存の検証済み zeroization 依存ライブラリ群を使い、所有する秘密バッファを drop 時に消去する。呼び出し側の入力・転送バッファは呼び出し側の責任であり、コンパイラ、アロケーター、OS のすべてのコピーの消去は保証しない。将来の明示的な転送アクセスも秘密を扱うことが分かる API とする。

ドメイン分離した authenticator を計算し、保守されている定時間比較プリミティブで 32 バイトすべてを比較する。一致位置で早期 return せず、受理済みトークンのコレクション全体を走査する。通常の XOR ループをコンパイラに影響されない時間特性プリミティブとして自作しない。選択するプリミティブの保証は等値比較に限り、レコード解析、hash の重複検証、認可全体を定時間とは呼ばない。

現在のビューと信頼したホスト時刻に対して認証する。不明トークン、失効済みトークン、無効主体、異なる audience、`now < issued`、`now >= expires` は一般的な認証拒否に統一する。`now >= time_floor` を要求し、無効・巻き戻ったホスト時刻は状態エラーとする。ホストはリクエストが指定した時刻を受け取らず、コミット前に再度時刻を読む。純粋な E01 API は決定的テストのため時刻を明示引数に取るが、その引数を選ぶのは信頼したホストアダプターだけである。

### 最新状態での操作ポリシー

認証は操作ごとの検査と冪等性検索より先に行う。使用前にパッケージ名を受理し、すべての検査で同じ現在のビューを使う。

| 操作 | 必要な現在の権限 |
| --- | --- |
| 所有者読取 | 名前が存在し、主体が所有者であるか、その名前への `admin` を持つ。メンバーの読取に変更権限は不要。 |
| 新規名取得と公開 | 名前が存在せず、その名前の `claim` と `publish` の両方を持つ。D02 がこの主体を最初の所有者として原子的に設定する。 |
| 既存名のバージョン identity の公開 | 名前が存在し、所有者資格と `publish` を持つ。D02 が不変バージョンと expected revision を別途検査する。 |
| yank または unyank | 名前が存在し、所有者資格と `yank` を持つ。 |
| 所有者変更 | 名前が存在し、所有者資格と `owners` を持つ。E03 が変更案と最後の有効所有者を別途検査する。 |
| 管理上の隔離・復旧 | 名前が存在し、その名前への `admin` を持つ。publish、yank、所有者変更のスコープを含意しない。 |

ローカルの主体・トークン登録と検証済みレジストリ復元には明示的で信頼した管理用ディレクトリ capability を使い、公開 wildcard admin トークンや未認証 HTTP endpoint を使わない。これは D02/E04 のトランザクションとして残る。

純粋な結果は、監査イベント用の受理済み主体 ID と非秘密のトークン ID のみを含む。情報であってシリアライズ可能な権限ではなく、後の変更 API が受け取る入力でもない。D02 は replay、expected revision 検査、変更より前に、ロック内で最新状態・時刻に対して実際の資格情報を再認証し、ポリシーを再評価する。D02 アダプターは受理したリクエストから操作を決定し、ネットワーク利用者が実際の変更より弱いポリシー操作を選べないようにする。

### 失敗と所有権の振る舞い

失敗時は静的メッセージを持つ上限付き構造化エラーを返す。bearer、token hash、生の JSON、入力パス、敵対的フィールドを展開しない。ポリシー呼び出しは I/O、ソース実行、永続化、時刻 floor 変更を行わない。不変で所有された検証済みレコードは信頼したホストコード間で共有できるが、存在だけでは最新性を証明しない。このホストプロトコル層では `unsafe`、guest object、backend 型、source span を扱わない。

## 実行モード

このホストレジストリポリシーは VM/native コンパイルから独立し、guest 実行 capability を付与しない。両プラットフォームで同じレコード・検査を用いる。D02 の実ストレージ・ネットワーク統合は別のプラットフォーム検証を要する。

## ABI と互換性

影響する領域は `package` と `tooling` である。言語 edition、ソース、MIR、bytecode、native ABI、component ABI は変えない。profile 1 は新しい内部版付き形式であり、不明な format/schema は拒否する。移行対象の出荷済みレジストリ権限状態はない。将来の schema 変更には明示的な移行・復旧判断を要し、以前拒否したトークンや audience を再解釈してはならない。

## 診断とツール

RFC 0046 の分類に従い、不正権限レコードは `REG0001`、資源上限拒否は `REG0002`、一般的な資格情報失敗は `REG0003`、操作拒否は `REG0004`、サービス identity 不一致は `REG0006`、無効・巻き戻った信頼時刻は `REG0007` とする。ネットワーク status 対応と利用者向け公開コマンドはアダプターの作業として残る。秘匿テストは error/debug 表示を検査する。ソース formatter、LSP、debugger の意味変更は不要。

## 性能とコストモデル

受理は 16 MiB、各コレクション上限、深さ 16 に制限し、上限付き set/map で参照と一意性を検証する。各認証は最大 4,096 個の固定長 authenticator を走査し、scope/owner 検査は 128 要素までとする。測定前に latency/throughput 目標を主張しない。zeroization と正規再エンコードには上限付きのメモリ・コピー費用があり、操作ごとのビュー全体 clone は避ける。

## セキュリティと信頼境界

受理済み権限オブジェクトが証明するのは構造的妥当性だけである。信頼は D02 の非公開ディレクトリ capability、検証済みコミット状態、ロックに由来し、アップロードされたオブジェクトをその状態として扱うのはセキュリティ欠陥である。正しい digest はトークン認証でもパッケージ来歴でもない。失効、所有権、時刻は変化するため、可視化点で検査する。盗難された有効な scoped bearer、悪意ある正規公開者、侵害されたホスト・運用者は RFC 0045 の残余リスクとして残る。

## 代替案

- **変更なし:** 公開境界のレコード・最新性契約が暗黙のまま残る。
- **外部 ID サービス・ライブラリ:** 将来の登録には有用だが、現在のパッケージ所有権、厳密なサービス audience、コミット時の原子的失効を定めない。上限付き E01 ポリシーには引き続きローカル契約が必要。
- **自己完結型の署名 access token:** 発行者を独立に検証できるが、現在の失効・所有者情報には依然として可変の信頼状態が必要。不透明な高エントロピートークンは RFC 0046 と一致し、別の token 署名・root lifecycle を避けられる。
- **キャッシュした主体・boolean:** 引数は減るが、古い scope/ownership や失効後 replay を許してしまう。監査用 identity を返し、毎回のコミットに実際の資格情報を要求すると、公開境界を明確に保てる。

## 実装計画

1. E01 実装前にこの補足仕様をレビューし、RFC 0046 の順序参照を更新する。D01 の検証が完了するまでは D01 のみを doing とする。
2. E01 を選択し、ホスト専用の上限付きレコード reader、秘匿 bearer 入力、最新状態ポリシーを実装する。振る舞いと不正入力の focused test を追加する。
3. baseline と両ホスト CI を実行し、英日 architecture/board の証拠を更新して作業ブランチを公開する。これは E01 のみの完了であり、G5 の完了ではない。
4. D02 はこの検査を囲む原子的ストレージを具体化・実装し、E02–E04 は別途追跡する所有者、復旧、監査 journey を追加する。

ブランチ準備: `carimatics/lang` の `codex/m5-registry-archive` の `b3c8d1b` から `codex/m5-registry-authority` を開始し、PR #33 に依存する。その依存が merge された後にのみ `main` へ retarget する。作業単位の開始ブランチは引き続き `main` で、新 checkout に既存のユーザー変更はなかった。

## テスト計画

- 正常認証と全操作の許可・拒否。admin と通常権限の分離を含む。
- 異なる名前、同じ registry ラベルの別 origin、不在・非所有パッケージ、無効主体、不明・失効トークン。
- issued/expiry/7 日/time floor の厳密な境界と、無効な信頼ホスト時刻。
- 失効・所有者削除後の再評価。D02 で replay 前の失効と body staging 中の変更を追加検証する。
- 正規 JSON、重複・未知フィールド、壊れた参照、重複 hash/ID、順序、整数表記、各割当・要素数・深さの境界。
- 63/64/65/66 バイトの秘密入力、任意 LF、禁止する CRLF/空白/大文字、上限付き reader、秘匿 error/debug 出力。
- panic のない決定的な敵対的入力変異と両ホスト CI。fuzz entry point を追加した場合は compile し、実行していない継続的 fuzz campaign は主張しない。

## 未解決事項

2026-10-31 JST、RFC 0001 の実験段階委任により採択。純粋なポリシーモデル `/private/tmp/lang-m5-authority-policy-model.js` は明示的な操作・audience・時刻の23ケースに成功し、retry成功後に資格情報失効・所有者削除を行うと同じ保持requestも拒否することを示した。これは判断用の証拠のみで、実際の認証やfilesystem transactionの実装ではない。レビューで曖昧なポート表現を修正し、受理時に独立した設定identityを要求した。監査identityと最新credential検査を分離し、E01/D02境界を明示した。本番資格情報転送、定時間比較・zeroization統合、D02の完全なstate/audit形式、実際のコミット時の最新性は未検証の実装義務として残る。採択はE01やG5の完了ではない。
