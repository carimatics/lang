## Summary

Implementation audited 2026-10-30 JST at `0b6591d`: manifest/graph/source admission, canonical standalone/workspace locks, real package commands and native reproducibility are reconciled with the implementation and acceptance tests `package_manifest, package_graph, package_source, package_lock, package_workspace, package_command, native_package`. The complete local baseline (174 suites / 2,514 tests, zero failures), fmt/full Clippy/doc and the macOS 15/Windows package and continuous installed-tool journeys pass. Acceptance-stage open-validation notes below are historical; this contract is implemented. This does not mean stabilized; the compatibility boundaries and non-goals below remain.

Introduce explicitly versioned `Lang.json` package/workspace manifests, local dependency resolution, `Lang.lock` and newline-delimited JSON CLI diagnostics. This is a host toolchain contract; it changes no source expression, typed MIR, runtime capability or ABI.

Accepted under RFC 0001's experimental delegation on 2026-10-29 JST. Exact local versions, explicit filesystem authority and fail-closed formats are a feasible first reproducible package profile. Registry transport, dependency namespace integration, both-host reproducibility and tooling ergonomics remain unverified until their deliveries have executable evidence. Acceptance is not implementation or stabilization.

## Motivation

The source CLI can compile a root file but cannot identify a package, resolve an authorized dependency graph or replay a checked source snapshot. M4 needs a create/depend/build/run/test fixture before expanding editor or installer infrastructure. M5's registry is not an implicit source of package authority.

## Goals

- Deterministic local package graphs and exact offline lock replay.
- Versioned, bounded, strict manifest/lock parsing and stable diagnostic envelopes.
- Reuse the existing source compiler, VM/native pipelines and source diagnostics.

## Non-goals

- Registry/Git/HTTP dependencies, version ranges, build scripts, macros, feature unification and automatic downloads.
- A source language edition change or changes to native/component ABI and existing artifact formats.
- Installer signatures, editor protocols and profiling contracts; those require separate M4 designs.

## Guide-level design

`Lang.json` is UTF-8 JSON, without comments or duplicate keys. A package example is:

```json
{
  "schema": 1,
  "package": {"name": "hello", "version": "0.1.0", "edition": "2026", "entry": "src/main.lang"},
  "dependencies": {"helper": {"path": "deps/helper", "version": "0.1.0"}},
  "tests": ["tests/smoke.lang"]
}
```

A workspace root has `"workspace": {"members": ["app", "helper"]}` and may also contain a package. A manifest must declare a package or a nonempty workspace; dependencies/tests require a package. Paths use `/`, regardless of host. Entries/tests/members are nonempty relative paths with no empty, `.` or `..` component. Dependency paths additionally permit `..` for workspace siblings, but the resolver must enforce the canonical authority boundary before reading them. Absolute paths, backslashes, colons and NUL are refused.

Package names and dependency aliases match `[a-z][a-z0-9_]{0,63}`. Versions are exactly three decimal u32 components, without leading zeroes, prereleases or build metadata. Edition is exactly `2026`. The library root uses the same `entry` field as a binary; package orchestration selects the appropriate compilation entry. The existing `mod`/`use`, privacy and ownership rules apply. Dependency aliases expose only declared direct dependencies, including when two dependencies use the same transitive alias. Namespace integration must preserve source bytes/spans, diagnose name collisions and prevent undeclared imports.

Package namespace clarification, accepted under experimental delegation 2026-10-29 JST: a root-level `mod helper;` binds the active direct dependency named `helper` when one is declared; otherwise it retains local file-module loading. This explicit declaration occupies the existing module namespace, so duplicate declarations/imports retain their existing diagnostics. `use helper::answer;` then imports a public item. A nested local module can reach it through `root::helper::answer`. In every package, `root::` begins at that package's entry module, including inside dependencies. A shared dependency has one module identity per compilation, while separate packages can use the same local/transitive names. Dependency `main` functions are ordinary functions; only the selected root's `main` is the execution entry. Existing visibility applies to every crossed item; `pub mod helper;` is an explicit public API edge, not ambient access to undeclared dependencies. An inactive dependency supplies no module binding. These rules add no source tokens or standalone-file behavior. Source keywords and the reserved `core` namespace retain their existing source diagnostics when used as module declarations.

The compiler host supplies a forest of package roots and declared edges, plus immutable parsed source snapshots. Package namespaces must not be implemented by concatenation or reparsing generated source. Compiler-internal qualified display names may distinguish dependency roots with an unspellable prefix; source paths and diagnostic spans remain original. Local file modules use the source directory containing their package entry, never a dependency's directory or the process working directory. The first execution checkpoint can snapshot reachable inputs; lock replay additionally requires the complete source inventory described below before compilation. This refinement is accepted because it reuses RFC 0006's explicit `mod` and privacy checks and allows canonical diamond reuse without synthetic declarations. Forest loading, duplicate-name/privacy diagnostics and VM/native equivalence require executable validation; both-host behavior remains unverified until CI.

The entry's containing directory is opened through the outer authority and retained as that package's source-directory capability. Entry and additional source files are opened relative to this handle; file symlinks escaping that source directory are refused even when their destination is inside the outer manifest authority. Directory aliases may resolve inside the outer authority before this handle is acquired. Opened regular-file metadata identifies duplicate source files (including hardlinks) without canonicalizing mutable final filenames. This source-admission clarification is accepted 2026-10-29 JST before implementation; it gives the package loader RFC 0006's narrower source-root boundary while preserving original display paths and bytes. No preexisting package execution format is migrated.

Windows implementation correction, 2026-10-29 JST: use the public `cap-fs-ext::MetadataExt` device/inode API for metadata obtained from an opened `File`. The similarly named `cap-std` trait does not expose the Windows handle fields on the pinned stable toolchain. This is host identity bookkeeping, with no new unsafe code, guest grant, source syntax or serialized field. Both-host hardlink refusal is required. The extension's 64-bit inode projection is its documented current limitation for 128-bit ReFS identifiers; a duplicate projection is refused, never used to run a second source as a separate identity.

Capture-lifetime revision accepted 2026-10-29 JST before implementation: directory capabilities live only during input capture. The first source preparation captures the complete bounded inventory once and releases every filesystem handle, including on admission failure. Subsequent analyses of that Graph use only its frozen paths/bytes/aliases, independent of file edits, deletion or project rename; a new filesystem epoch requires a new Graph. Cache a capture failure rather than reopening mutable inputs. Windows CI demonstrated that retaining directory handles through analysis prevents the existing positive project-rename fixture. This revision separates immutable compiler data from temporary I/O authority, preserving the rename requirement and the original byte/span contracts. Source parsing/typing still reports its original diagnostics after capture; filesystem/resource admission failures may precede it with package diagnostics. No runtime or serialized version changes.

`targets` on a dependency is an optional nonempty list of exact target triples: `aarch64-apple-darwin` and `x86_64-pc-windows-msvc`. Absence includes both; duplicates and unknown triples are errors. Resolution selects one explicit supported target, defaulting to the host; target changes invalidate lock replay. Validate all declarations before filtering inactive dependency edges.

Planned commands are `lang new DIR`, `lang build`, package-aware `lang run`, `lang test`, `lang package`, `lang fmt`, `lang lint` and `lang doc`. Package commands accept `--manifest-path`, `--target`, `--offline`, `--locked` and `--message-format human|json` where applicable. `lang package check-manifest FILE` is the first inspection operation and does not grant dependency I/O. Existing explicit-file CLI forms retain their behavior.

### Package command transaction profile

Accepted under experimental delegation, 2026-10-29 JST, before package command implementation. Package forms are `lang new DIR [--name NAME] [--message-format human|json]` and `lang build|run|test [--manifest-path FILE] [--target TRIPLE] [--locked] [--offline] [--message-format human|json]`. With no manifest option, use exactly `./Lang.json`; do not search ancestors. The target defaults to the supported host triple. Run/test also accept the existing fuel, service-work, host-call, frame and cell limits. Duplicate/unknown/missing options are usage errors. Existing explicit-file `run`, `run --artifact`, `check`, `compile`, `native`, REPL and integer forms retain their behavior. A positional source or `--artifact` selects legacy `run`; package-only options mixed with a positional source are refused. A run without a source selects the package form.

`new` writes an explicit schema-1 package at version `0.1.0`, edition `2026`, entry `src/main.lang`, with `tests/smoke.lang`; both generated mains return zero. The package name is `--name`, or the directory basename only when it already satisfies the manifest name grammar. An invalid basename requires an explicit name; do not silently rewrite it. Publish a complete new directory exclusively, refusing any existing destination, including an empty directory. Do not modify an existing project or infer/fetch dependencies. Scaffold files use UTF-8/LF. Build/new/test success is silent; run prints its i64 result plus LF and exits zero after successful execution/publication. A test's zero result passes; nonzero or runtime failure exits one with a diagnostic. There are no additional success JSON records; JSON mode governs stderr diagnostics as already specified.

Build/run compile the selected package entry through the existing verified portable artifact profiles, including Copy, ownership and structured tasks/services. Test compiles each explicitly declared test entry using that entry's frozen source-directory scope, the same dependency forest and original bytes/spans; it must not synthesize source or reread files. Zero tests still type-check the package graph but do not require an executable main. Tests stop on the first failure. Reuse the existing VM engines and allocator/control contracts; do not implement a second package interpreter. Native executable/link integration remains A06 and must not be claimed from this portable checkpoint.

Test namespace clarification, accepted under experimental delegation 2026-10-29 JST before A04 implementation: execute only the selected package's tests, in manifest order. A separate test entry is the root namespace of its analysis, with the selected package's active direct dependencies and an additional test-only edge named `_package` to the selected package. For example, `mod _package; fn main()->i64 { return _package::answer() + -42; }` tests a public answer without executing the package's main. The leading underscore is valid source syntax but invalid as a manifest dependency name, so this fixed alias cannot collide with a declared dependency. It grants ordinary public module access, no private access or runtime capability. Each original package keeps its own `root::` and nominal identity. If a declared test is exactly the package entry, reuse that existing root instead of loading a duplicate canonical file. Ordinary duplicate-module/cycle rules continue to apply. The additional test root counts against the existing module limits. No generated source or serialized package edge is introduced; a future change of this behavior must invalidate the compiler identity. Compared with a new assertion syntax or source wrapper, this uses the existing main/visibility/module contracts. Frozen-scope/own-export/privacy/profile/failure fixtures must validate the choice; no ergonomics or performance improvement is assumed.

Implementation clarification, 2026-10-29 JST: each entry uses a fresh VM instance and the supplied per-entry execution controls. Bound retained test artifacts during compilation by the same 64 MiB output limit. Executable fixtures corrected the example above to the existing addition/signed-literal syntax.

For failure-safe publication, derive a generation key from SHA-256 of canonical lock bytes. Build/run generations are `target/lang/<key>/build/` with `inputs.lock` and `main.lbc`; test generations are `target/lang/<key>/test/` with `inputs.lock` and `tests/<manifest-index>.lbc`. The `inputs.lock` copy is exact and makes even a zero-test generation nonempty. This layout is private tool output, not a source or component ABI. Stage a complete generation privately in the same parent, publish exclusively, and never replace a prior generation. An existing generation must match freshly verified expected files/bytes before reuse; cached data never substitutes for source/lock verification. Bound total staged output, including the lock copy, to 64 MiB per operation and retain existing source/format bounds.

Hold output-directory authority separately from source capture. Refuse reserved-output collisions with admitted manifest/source inputs, including physical aliases, before writing. Validate the lock before typing in locked mode; compile/verify every artifact and complete run/test execution before publishing a generation. Publish the root `Lang.lock` last as the sole mutable commit point; `--locked` never rewrites it. Failure retains the prior lock and its build/test generations. Remove private temporary stages; a completed unreferenced immutable cache generation may remain after lock-publication failure, because a concurrent operation could have adopted it. No rollback may delete another operation's committed generation. Offline mode performs only authorized local I/O, with no network fallback.

Rationale: separate replacement of a fixed artifact path and the lock cannot provide one atomic commit point. Immutable generations plus the final lock publication preserve previous output without a multi-file rollback journal. Leaving fixed mutable output paths unchanged, publishing the lock first, or recompiling from mutable paths after lock validation would not meet that contract. This clarifies previously unimplemented CLI/output behavior and changes no existing lock/artifact schema. Both-host exclusive directory publication, concurrent reuse, test-entry/profile integration and resource/failure cleanup require executable A04 evidence; no performance improvement is assumed.

### Workspace selection and lock schema 2

Accepted under experimental delegation, 2026-10-29 JST, before workspace implementation. Build/run/test add `--package NAME`. With an explicitly selected workspace manifest, choose its root package when present and no name is supplied; a workspace-only root requires a name. Named selection uses package identity, including the root package as implicit member `.` when present. Validate every explicitly listed member manifest once, require a package, and reject duplicate canonical directories or package names with `PKG0006`. Nested workspace declarations are not recursively expanded. Missing/unknown selection is `PKG0006`; malformed command options retain `CLI0001`/exit 2. A standalone named selection must match that package and grants no containing-directory authority. No ancestor search or implicit first/all-member selection is added.

The explicit manifest's directory remains the authority and output root. A workspace root authorizes declared dependencies anywhere inside that directory, including siblings; all existing containment, regular-file, cycle, exact-version and resource checks apply. Freeze root/member metadata before resolving the selected dependency graph, and reuse those bytes instead of rereading a checked manifest. Only the selected graph's source entries are prepared. Keep all catalogue member roots excluded when nested beneath another package's source traversal, while retaining explicitly declared source scopes. Known manifest paths remain metadata inputs. Account every admitted manifest, including unselected members, in output-alias/reserved-path checks. Source capture still closes its handles and compilation uses only frozen inputs. Workspace operations share the root `Lang.lock` and `target/lang/<key>/` generations; a standalone member operation keeps its own authority/output root.

Standalone locks retain schema 1 and its exact encoding/checksum fixture. Workspace operations use schema 2 with ordered top-level fields `schema`, `target`, `compiler_version`, `compiler_build_id`, `workspace`, `packages`. Package records/checksums retain schema-1 fields and encoding. The required workspace record has fields `manifest_path`, `manifest_sha256`, `members`, `selected_root`, `checksum`. Each member has `path` (declared directory, or implicit `.`), `root` (canonical authority-relative directory), `manifest_path`, `manifest_sha256`, `name`, `version`. Sort members by UTF-8 `path`. Include the root package in this list when present. Root/member metadata is bounded by one root plus the existing 128-member limit, at 64 KiB per manifest; retain the 1 MiB lock bound, two-space UTF-8 JSON and final LF. Paths retain schema-1 normalization.

The workspace checksum starts with `LANGWORKSPACE1` plus NUL, then little-endian u64 unique metadata-file count. Sort root/member manifest files by canonical authority-relative path, counting a root package's manifest only once. Each contributes u64 UTF-8 path length, path bytes, u64 original content length and original bytes. Append u64 member count, then each sorted member's `path`, `root`, `manifest_path`, `name`, `version`, each length-prefixed as u64 UTF-8 bytes. Finally append length-prefixed `selected_root`. SHA-256 uses lowercase hex. This pins unselected manifests, declared/canonical bindings and selection without treating metadata as language sources or inventing package identities. Publish an independently calculated canonical fixture before replay uses schema 2.

The independent schema-2 fixture is [`tests/fixtures/package-lock/schema2-workspace.json`](../../tests/fixtures/package-lock/schema2-workspace.json), checked by `tests/package_workspace.rs`. Its workspace checksum is `a672b45db910fc7f615e083b7fa3f33fca975bd716640a00a4ff5e726a49134a`; only the compiler build identity is substituted. The fixture was calculated independently before schema-2 replay implementation.

Decode a bounded schema header, then the matching strict schema-1 or schema-2 shape; reject duplicate/unknown fields and unsupported versions. Pure encoding validation grants no replay authority. Locked verification compares with the freshly captured complete canonical record before typing. A changed workspace manifest, member manifest, binding, selection or active source refuses without rewriting prior output; inactive/unselected source files are not read merely for catalogue validation. Tests execute only the selected package's declarations with the A04 namespace/control contract. Both supported targets retain exact target-condition graphs and compiler identities.

Rationale and compatibility: the executable pre-implementation probe refuses a virtual root and standalone sibling access, and a root-package schema-1 lock remains accepted after an unselected member manifest changes. Schema 1 has no typed slot for that input. A workspace record preserves input roles and the old standalone fixture; a wrapper cannot pin the missing authority/metadata, and overloading source/package records would obscure their contracts. Existing standalone encoding remains supported. Old binaries refuse workspace schema 2; an earlier package-only lock for a workspace requires ordinary unlocked regeneration. There is no automatic migration. Manifest/source syntax, artifact schemas, guest capabilities and native ABI are unchanged. Member alias containment, metadata freeze/handle release, relocation, both-target replay and failure preservation require executable evidence; native package reproducibility remains A06. No performance improvement is assumed.

### Native package build profile

Accepted under experimental delegation, 2026-10-29 JST, before CLI implementation. `lang build --native --sdk SDK` compiles the same frozen selected package graph, emits the existing native program profile and links its default startup through the explicit matching SDK. Both options are required together and belong only to build; usage errors remain `CLI0001`/exit 2. A complete native executable targets the current host; another target is `PKG0003` before output. Existing Copy/owned/task startup and explicit-host refusals for C/components remain unchanged. Build executes no guest entry and performs no source reread or Cargo/network operation.

The linker returns the exact verified SDK manifest bytes from its private snapshot. Publish the native program files, `sdk-input.json`, executable `application`/`application.exe`, `inputs.lock` and canonical `build.json` together under `target/lang/<lock-key>/native-<sdk-manifest-sha256>/`. SDK identity hashes original admitted manifest bytes, whose verified file table pins the copied SDK inputs. Native and portable generations remain independently reusable. Preserve executable permissions on Unix and verify them during cache admission. Reuse the 128-output/64-MiB package generation bounds and final-lock transaction; compilation, SDK/toolchain/link, size, stale-lock or cache refusal preserves prior outputs.

`build.json` is UTF-8 JSON with two-space indentation and final LF, ordered fields `schema` (1), `target`, `compiler_build_id`, `lock_sha256`, `sdk_manifest_sha256`, `rustc_release`, `rustc_commit`, `package_manifest_sha256`, `executable_sha256`. Identity/toolchain data comes from frozen compiler inputs and the checked SDK/link operation. Cache replay compares complete expected canonical output bytes; a receipt grants no execution authority. A successful native build prints the authority-relative executable path; JSON message format emits one object with ordered `schema` (1), `kind` (`artifact`), `path`. Errors retain existing diagnostics.

Rationale: composing the existing compiler/SDK/link APIs preserves original entry, spans, native trust and compatibility without another backend or startup engine. A manual two-command recipe does not freeze package dependencies or commit its outputs with the package lock. Keeping native output under the portable generation would conflate SDK-dependent inputs. The source/lock/native/SDK schemas are unchanged; this adds an independently versioned build receipt and CLI profile. The reproducibility probe exposed startup/debug-map staging paths; RFC 0020 records their correction before implementation. Full executable digests, source-free startup, failure preservation, SDK mismatch and both-host behavior require tests. Reproducibility is limited to fixed SDK and external native toolchain inputs, not a cross-toolchain or cross-host byte identity claim. The reviewed A06 task list remains one 3-point executable outcome using existing admission/publication mechanisms.

## Reference semantics

Manifest schema 1 rejects missing required and unknown fields, duplicate keys at every object level, unsupported schema/edition, malformed names/versions/paths/conditions and trailing input. No default package identity or inferred dependency path is allowed. Optional dependencies/tests default to empty; optional workspace defaults to absent. An optional field, when present, must have its declared type; explicit null is not omission. Manifest bytes are limited to 64 KiB, each dependency/member/test list to 128 entries. JSON nesting retains serde_json's bounded recursion limit.

Pre-merge input-admission revision, accepted under experimental delegation 2026-10-29 JST: file inspection accepts regular files only and refuses directories, devices and FIFOs with `PKG0005`. On Unix, open nonblocking before checking metadata on the opened handle, so a FIFO without a writer cannot block the admission check. The existing native SDK reader supplies this implementation pattern. A bounded CLI experiment reproduced the former blocking open; stream input was never part of this profile. This clarifies file admission without changing manifest bytes or versions; the byte limit plus sentinel still applies to growing regular files.

Resolution starts from an explicit manifest. Its directory is the authority root; an explicitly selected containing workspace can authorize sibling members. Canonical dependency roots, entries and source files must remain inside that root, with symlink escapes refused. Local dependency identities are canonical root plus declared name/version. Alias must equal the dependency name in schema 1. Resolve edges in sorted alias order, reject cycles, duplicate identities with conflicting contents, mismatched exact versions and missing sources. Limits: 256 packages, 256 modules, 16 MiB total source bytes and 4096 edges; account repeated graph visits. No build script or dependency code executes during resolution.

Dependency-I/O clarification accepted 2026-10-29 JST: resolve package directory identities using directory-only operations. Preserve admitted authority-relative file paths in snapshots and enforce resolved-file containment during capability-relative, nonblocking regular-file opens. Do not canonicalize an unchecked file before admission or reopen its mutable pathname for identity after validating a different handle: a bounded experiment showed file canonicalization itself can wait on a FIFO. This changes no manifest syntax, version or runtime authority.

`Lang.lock` schema 1 records selected target, toolchain/package edition, sorted package identities using authority-relative `/` paths, exact versions, sorted active edges and SHA-256 source/manifest checksums. Hashes cover original bytes, with length-prefixed paths and bytes in lexical order; no absolute host paths, mtimes or filesystem enumeration order enter identity. Every `.lang` source beneath a package source root is included; generated output, nested dependency roots and symlink escapes are excluded/refused explicitly. Compiler source-root access must be restricted to those inputs. The lock implementation must document its canonical byte encoding and fixture before being used for replay.

Ordinary resolution creates/updates the lock transactionally after complete validation. `--locked` refuses a missing/stale lock and never rewrites it. `--offline` permits only authorized local files and performs no network operation; combined with `--locked` it checks all identities, edges and checksums before compilation. No stale source or cached binary substitutes for a mismatch. Write outputs through same-directory temporary files and atomic publication; failures retain previous lock/build output. Concurrent source changes must invalidate publication or use the verified immutable snapshot. A content digest supplies integrity, not publisher authentication.

### Lock schema 1 encoding

Accepted clarification, 2026-10-29 JST, before A03 implementation: lock fields in order are `schema`, `target`, `compiler_version`, `compiler_build_id`, `packages`. Each package has `root`, `name`, `version`, `edition`, `manifest_path`, `manifest_sha256`, `sources`, `dependencies`, `bindings`, `checksum`. A source has `path`, `sha256`; an edge has `alias`, `root`. A binding has `kind` (`directory`, `entry` or `test`), `scope`, `path`, `target`. It pins declared entry/test paths to frozen input keys and directory aliases to their frozen targets within each canonical source scope. Package records sort by authority-relative root; sources by path, edges by alias and bindings by `(scope, kind, path, target)`, using UTF-8 lexical order. Root/scope `.` denotes the authority directory; all other paths use normalized authority-relative `/` components without `.` or `..`. No absolute path or filesystem identity is persisted. The compiler version is the crate version; its build identity is the existing production-source/toolchain/profile fingerprint paired with the selected target. A different compiler identity requires ordinary lock regeneration; locked mode refuses it.

SHA-256 digests use lowercase hex. A package checksum starts with bytes `LANGPACKAGE1` followed by NUL, then a little-endian u64 file count. The file list contains the manifest and source inputs sorted by path, with duplicate input paths refused. Each file contributes little-endian u64 UTF-8 path length, path bytes, little-endian u64 content length and original content bytes. Append a little-endian u64 binding count, then each sorted binding's `scope`, `kind`, `path`, `target`, each as a little-endian u64 UTF-8 byte length followed by those bytes. Per-file hashes cover only original content bytes. Canonical lock bytes are UTF-8 JSON using the listed field order, two-space indentation and one final LF, as pinned by the serialization fixture. Parsing rejects duplicate/unknown fields and unsupported schema versions; replay also requires byte-for-byte canonical equality with the newly verified expected lock. Bound lock reads to 1 MiB plus one detection byte and retain bounded JSON nesting.

Binding-integrity revision accepted 2026-10-29 JST before any lock implementation: file checksums alone cannot pin resolution. A directory alias can switch between two already inventoried trees while every canonical file path/content stays unchanged, yet select another function body. Entry/test directory aliases can similarly change selection when inventories overlap. Persist these resolved bindings and include them in the package checksum; retain every declared entry/test-to-input mapping even when files or scopes overlap. Numeric inode/device values remain transient duplicate-admission data. A03 must execute a retargeted-alias refusal with unchanged source files and preserve the previous lock/output. This changes the not-yet-implemented schema-1 contract; there are no existing lock artifacts to migrate.

The complete inventory covers each declared entry/test source directory and explicit entry, including unused `.lang` files. Deduplicate overlapping source roots; exclude nested dependency package roots and each package's root `target` output directory, plus `.git`/`.codex` metadata directories. The root output directory is reserved by package orchestration; a `src/target` module directory remains a source input. Charge source files against the 256-module/16-MiB limits and cap all visited directory entries, including non-source entries, at 4096. Traverse deterministically through retained directory capabilities, refusing escaping links, duplicate physical source identities and directory cycles. Compilation after lock verification must use this frozen inventory and perform no further source reads. These bounds and canonical bytes are project choices, not measured performance claims. Executable relocation, stale/unused-source, target/compiler mismatch, malformed-lock, resource and atomic-publication fixtures remain A03 acceptance work.

The schema-1 serialization fixture is [`tests/fixtures/package-lock/schema1.json`](../../tests/fixtures/package-lock/schema1.json); only the compiler build identity is substituted at test time. Its manifest/source/package SHA-256 values are independently pinned. `tests/package_lock.rs` also pins UTF-8 ordering for U+E000 and U+10000 paths, which have the opposite UTF-16 order. These fixtures document the canonical bytes before package CLI replay is introduced.

Source evaluation order, typing, ownership/destruction, cancellation, concurrency, const evaluation and foreign capabilities retain their accepted semantics. Package loading grants host compiler read authority only; guest runtime authority remains explicit.

## Execution modes

VM, native AOT and JIT consume the same checked source graph. Package tests are explicit source entries with `fn main()->i64`; zero passes and nonzero fails. Runtime failure fails the test. Native builds use existing target/SDK/link admission and record their toolchain inputs; a portable artifact alone does not establish the reproducible native-binary gate. Embedded/component artifacts keep explicit bindings and independently versioned formats.

## ABI and compatibility

Compatibility domains are `package` and `tooling`. Manifest, lock and diagnostic schema versions are independent of bytecode, native SDK and component C v1 versions. Unknown versions are errors, never guessed migrations. No preexisting package manifest is being migrated. Future changes that invalidate schema 1 require an RFC revision and explicit migration/refusal tests. Existing source commands and human diagnostics remain compatible.

## Diagnostics and tooling

JSON mode emits one complete JSON object per stderr line, with no human prose mixed in. Schema 1 diagnostic objects contain `schema: 1`, `kind: "diagnostic"`, `code`, `severity: "error"|"warning"|"note"`, `message`, `path` (string or null), and `span` (null or `{start,end}` UTF-8 byte offsets in that path). Optional contextual detail belongs in a future version, not ad hoc fields. Source diagnostics retain their stable existing codes and original spans; package errors use `PKG0001` malformed input, `PKG0002` unsupported version, `PKG0003` invalid contract field, `PKG0004` resource limit, `PKG0005` filesystem/authority, `PKG0006` dependency graph, `PKG0007` lock mismatch. Usage errors use `CLI0001`; tool/runtime failures without a more specific diagnostic use `CLI0002`. Exit status remains 2 for usage and 1 for source/tool/runtime failure, 0 for success. Program results remain stdout; command-specific success records must be explicitly documented before implementation. Error locations may be absent for manifest semantic validation; never fabricate an offset.

Formatting/lint/doc operate on the declared verified package inputs. Editor overlays and debugger source mappings use original paths/spans, not generated concatenated source. Package syntax does not change the source formatter. Further LSP/DAP/code-action designs must state their edit and snapshot invariants.

## Performance and cost model

Parse memory/work is bounded by manifest bytes and list limits. Graph traversal and hashing consume explicit package/edge/source limits; byte hashing and canonical sorting are visible build work. Cache hits require matching source, target and toolchain identities. No timing or binary-size improvement is claimed without measurements.

## Security and trust boundaries

Treat manifests, locks and dependency sources as untrusted input. Reject path traversal outside the explicit canonical authority, symlink escapes, invalid UTF-8, unknown fields/versions and oversized input before allocating unbounded structures. Do not invoke a shell, fetch a registry, load native plugins or grant guest capabilities during resolution. Local path checks must not imply race-resistant isolation; immutable verified snapshots and handle-relative access are required before publishing output under concurrent changes.

## Alternatives

- No change leaves M4's reproducibility and onboarding gates unsatisfied.
- A shell wrapper around source commands cannot independently verify the package graph or provide the diagnostic contract.
- Cargo-like TOML manifests and range resolution are a strong alternative, but add a format/parser and solver/registry policy before the first local fixture. Exact JSON fits the existing serde stack and keeps authority inspectable. Ergonomics remain an open measurement, not a claim of superiority.
- Concatenating dependencies or ignoring checksums is simpler but loses source namespaces/spans or reproducibility. It does not satisfy this design.

## Implementation plan

1. Strict manifest parser and structured diagnostic inspection, with malformed-input/resource-limit fixtures.
2. Authorized deterministic local graph and exact lock/replay tests.
3. Create/local-dependency/build/run/test fixture, including changed-source offline refusal; then native reproducibility.
4. Package/fmt/lint/doc integration and the broader M4 editor/debug/installer deliveries.

Use [the M4 board](../milestone-4.md) for observable 1–3-point deliveries, validation and estimate changes.

## Test plan

Round-trip admitted manifests; reject duplicates, missing/unknown fields, unsupported editions/versions/targets, invalid paths, cycles, version mismatches, escapes, stale locks and resource exhaustion. Verify JSON lines and exit status with real CLI processes. The first package fixture must create a project and local dependency, compile/run/test, replay offline exactly and refuse modified input without changing prior output. Check VM/native values and spans, relocation-independent lock identity, target changes, both tier-1 hosts and repeated binary digests with pinned toolchain inputs. Fuzz parser/lock boundaries when implemented; do not equate finite malformed tests with a fuzz campaign.

## Open questions

- Registry identity, signing and version ranges belong to M5, not implicit fallback behavior.
- Installer/editor/profiling protocols remain separate accepted-design work on the board.
- JSON ergonomics, immutable package snapshot costs and reproducible native linking require evidence; revise explicitly if the measured design must change.
